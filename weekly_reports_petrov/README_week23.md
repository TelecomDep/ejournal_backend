## Часть 1. Фиксация согласия на обработку персональных данных

Для хранения решения пользователя добавлена таблица `user_agreement_decisions`. Она сохраняет не только само решение, но и контекст, в котором оно было принято:

```sql
CREATE TABLE user_agreement_decisions (
    decision_id   BIGSERIAL PRIMARY KEY,
    user_id       INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    agreement_key TEXT NOT NULL DEFAULT 'user_agreement',
    version       TEXT NOT NULL,
    decision      TEXT NOT NULL CHECK (decision IN ('accepted', 'declined')),
    decided_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    document_hash TEXT,
    ip            INET,
    user_agent    TEXT
);
```

Добавлен индекс по пользователю, ключу соглашения, версии и времени решения. Благодаря этому можно быстро получить последнее решение по конкретной версии документа.

Добавлены два маршрута:

- `POST /api/user/agreements/decision` — сохранить решение `accepted` или `declined`;
- `GET /api/user/agreements/current` — получить текущую версию соглашения и последнее решение.

Решение связывается с пользователем по JWT-токену. Передача чужого `user_id` не используется. Backend проверяет, что версия соглашения является актуальной, а само решение содержит допустимое значение.

Пример ответа проверки соглашения:

```json
{
  "ok": true,
  "result": {
    "agreement": "user_agreement",
    "version": "2026-08-01",
    "decision": "accepted",
    "accepted": true,
    "decided_at": "2026-08-14T12:30:00+07:00"
  }
}
```

Для записи решения в request envelope добавлены метаданные запроса: IP-адрес и User-Agent. Это позволяет сохранить технический контекст принятия согласия.

## Часть 2. Выгрузка для общего рейтинга

Добавлена ручка:

```text
GET /api/staff/ratings/general?semester_id=7
```

Если `semester_id` не передан, используется открытый семестр. Авторизованный преподаватель получает только собственные группы и предметы. Руководящие роли получают данные в пределах своей области видимости: кафедры, факультета или всей организации.

Ручка объединяет данные из расписания, семестров, групп, студентов, предметов, посещаемости и оценок. В результате формируется единая структура, пригодная для построения общего рейтинга:

- сведения о семестре;
- роль и идентификатор пользователя в `access_control`;
- кафедры и предметы с преподавателями;
- группы и студенты;
- статус согласия каждого студента;
- посещаемость по датам;
- лабораторные и практические работы;
- процент успеваемости и посещаемости по предмету.

Для студента формируется стабильная ссылка вида `STU-0001`. Если оценка ещё не выставлена, `score` возвращается как `null`. Уважительные пропуски не включаются в знаменатель посещаемости, а статусы `present` и `late` считаются посещением.

## Часть 3. Стандартная API-обёртка


```json
{
  "id": "http-general-rating",
  "ok": true,
  "result": {
    "schema_version": "1.0",
    "semester": {
      "semester_id": 7,
      "title": "Весенний семестр 2025/2026"
    },
    "access_control": {
      "role": "teacher",
      "user_id": 42,
      "allowed": true
    },
    "departments": [],
    "subjects": [],
    "groups": []
  },
  "error": ""
}
```

Ошибки этой ручки также используют стандартный `app.Response` и получают идентификатор `http-general-rating`. Это позволяет frontend одинаково обрабатывать рейтинговую выгрузку и остальные API-запросы.
