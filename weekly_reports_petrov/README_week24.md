# Неделя 24


## Часть 1. Проверка и усиление безопасности backend

На этой неделе была проведена проверка безопасности сервиса. Основное внимание было уделено авторизации, одноразовым кодам, состоянию учётных записей и защите служебных маршрутов.

Для возможности принудительно завершать ранее выданные сессии в таблицу пользователей добавлено поле `token_version`. Значение версии записывается в JWT. При каждом запросе backend сравнивает версию из токена с текущим значением в базе данных. Если администратор изменил состояние пользователя или версия была увеличена, старый токен перестаёт работать.

Для подтверждения привязки электронной почты и включения двухфакторной аутентификации добавлена таблица `auth_challenges`:

```sql
CREATE TABLE auth_challenges (
    challenge_id BIGSERIAL PRIMARY KEY,
    user_id      INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    purpose      VARCHAR(32) NOT NULL,
    target       TEXT NOT NULL DEFAULT '',
    code_hash    BYTEA NOT NULL,
    attempts     SMALLINT NOT NULL DEFAULT 0,
    expires_at   TIMESTAMPTZ NOT NULL,
    consumed_at  TIMESTAMPTZ,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

Код подтверждения не хранится в открытом виде. Backend вычисляет HMAC-SHA256 на основе пользователя, назначения операции и самого кода. Сравнение выполняется за постоянное время. Для одного кода разрешено не более пяти попыток, после успешного применения или исчерпания попыток запись становится недействительной.

Дополнительно выполнены следующие изменения:

- служебный маршрут `/metrics` закрыт заголовком `X-Metrics-Token`;
- при неправильном токене метрик возвращается `404`, поэтому маршрут не раскрывает своё назначение;
- добавлен режим технического обслуживания с ответом `503` и заголовком `Retry-After`;
- проверяется статус учётной записи, поэтому заблокированные и архивные пользователи не могут продолжать работу со старым JWT;
- Docker-образы backend и вспомогательных сервисов переведены на запуск от непривилегированного пользователя;
- расширена модель ролей и их областей доступа.

## Часть 2. Сводная посещаемость студента

Добавлена новая ручка:

```text
GET /api/student/attendance/summary?semester_id=2
```

Если `semester_id` не указан, используется открытый текущий семестр. Пользователь определяется только по JWT, поэтому студент не может запросить посещаемость другого человека.

Ответ содержит общую сводку и показатели по каждому предмету:

```json
{
  "ok": true,
  "result": {
    "student_id": 2,
    "semester_id": 2,
    "subjects": [
      {
        "subject_id": 1,
        "subject_name": "Networks",
        "total_sessions": 41,
        "attended_sessions": 28,
        "excused_sessions": 0,
        "missed_sessions": 13,
        "attendance_percent": 68.29
      }
    ],
    "summary": {
      "total_sessions": 41,
      "attended_sessions": 28,
      "excused_sessions": 0,
      "missed_sessions": 13,
      "attendance_percent": 68.29
    }
  }
}
```

Статусы `present` и `late` считаются посещением. Уважительные пропуски `excused` показываются отдельно и исключаются из знаменателя. Процент рассчитывается по формуле:

```text
attendance_percent = attended_sessions / (total_sessions - excused_sessions) * 100
```


## Часть 3. Оценки по предметам вместе с посещаемостью

Расширена существующая ручка:

```text
GET /api/student/grades/all
```

Раньше она возвращала контрольные точки, оценки и суммы баллов по предметам. Теперь в каждый предмет дополнительно включены:

- `total_sessions`;
- `attended_sessions`;
- `excused_sessions`;
- `missed_sessions`;
- `attendance_percent`.

Общая посещаемость также добавлена в `result.summary`. В результате frontend может одним запросом построить экран оценок, показать баллы по каждому предмету и рядом отобразить процент его посещаемости.

Для получения данных используется расписание группы выбранного студента и записи `attendance_session_students` за тот же семестр. Это не позволяет смешивать оценки одного семестра с посещаемостью другого.

## Часть 4. Расписание студентов и преподавателей

В backend уже существовал обработчик расписания студента, но HTTP-маршрут не был зарегистрирован при запуске сервера. Поэтому запрос frontend фактически получал `404`, несмотря на наличие SQL-кода. Маршрут был подключён:

```text
GET /api/student/schedule/day?date=2026-08-20
```

Также добавлено расписание текущего преподавателя:

```text
GET /api/teacher/schedule/day?date=2026-08-20
```

Идентификатор преподавателя берётся из JWT и связанного профиля. Передать чужой `teacher_id` через query-параметр нельзя.

Для каждой пары возвращаются:

```json
{
  "schedule_id": 5,
  "lesson_num": 99,
  "start_time": "11:22",
  "end_time": "12:52",
  "subject_id": 1,
  "subject_name": "Networks",
  "group_id": 2,
  "group_name": "TEST-GROUP-1",
  "lesson_type": "Практика",
  "room_info": "",
  "subgroup": ""
}
```

Расписание читается из таблиц `schedules`, `lesson_times`, `subjects`, `groups` и `semesters`. Учитываются день недели, числитель/знаменатель и семестр, которому принадлежит дата. Разрешён просмотр текущей и следующей календарной недели. Неверный формат даты возвращает `400`, пользователь с неправильной ролью получает `403`.

## Часть 5. Проверка управления семестрами

Проверена возможность администратора создавать новые учебные семестры. В сервисе уже реализован маршрут:

```text
POST /api/admin/semesters
```

Доступ разрешён только роли `admin`. Преподаватель при обращении к этому маршруту получает `403 Forbidden`.

При создании проверяются:

- формат учебного года `YYYY/YYYY`;
- последовательность годов;
- номер семестра;
- название и диапазон дат;
- отсутствие пересечения с существующими семестрами;
- допустимый начальный статус `planned` или `open`.

Также сохранены маршруты активации, закрытия, архивирования и удаления запланированного семестра. В ходе проверки администратор успешно создал тестовый семестр, после чего он был удалён. Тестовые данные после проверки очищены.
