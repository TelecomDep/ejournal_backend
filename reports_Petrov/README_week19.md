# Неделя 19 

## Часть 1. Backend: ускорение сводок и устранение узкого места при логине

На этой неделе основной фокус был на backend. Сначала была закрыта проблема этапа 0: самый тяжёлый экран со сводкой по студентам упирался не в PostgreSQL как таковой, а в неудачную форму запроса. В `/api/staff/overview` группы, студенты и посещаемость соединялись так, что промежуточный набор раздувался до произведения, из-за чего запрос уходил в таймаут.

Исправление оказалось в перестройке запроса на CTE с отдельной агрегацией по студентам и посещаемости. Заодно вынесена более лёгкая постраничная ручка для таблицы студентов потока и убран N+1 в выдаче всех оценок студента, чтобы не добирать предметы и оценки отдельными запросами на каждую строку.

Отдельно добавлена базовая наблюдаемость по нагрузке:
- `internal/httpserver/metrics.go` - защищённый `/internal/metrics` с токеном `METRICS_TOKEN`;
- `internal/db/query_metrics.go` - замер статистики SQL-запросов;
- `internal/db/store.go` - подключение трассировки к пулу `pgx`;
- `internal/app/service.go` - сводка по очереди задач и пулу соединений.

Маршруты и защита метрик выглядят так:

```go
fiberApp.Use(s.metricsMiddleware)
fiberApp.Get("/internal/metrics", s.internalMetricsHandler)
fiberApp.Get("/api/staff/overview", s.staffOverviewHandler)
fiberApp.Get("/api/staff/overview/students", s.staffStudentsPageHandler)
```

```go
func (s *Server) internalMetricsHandler(c *fiber.Ctx) error {
	expectedToken := s.cfg.MetricsToken
	providedToken := c.Get("X-Metrics-Token")
	if expectedToken == "" || subtle.ConstantTimeCompare([]byte(expectedToken), []byte(providedToken)) != 1 {
		return c.SendStatus(fiber.StatusNotFound)
	}
	return c.JSON(fiber.Map{
		"http":    s.metrics.snapshot(),
		"runtime": s.svc.RuntimeStats(),
	})
}
```


## Часть 2. Backend: мягкое удаление оценок и аудит действий

Вторая крупная часть недели - подготовка безопасного удаления оценок. Раньше оценка и контрольная точка жили как обычные записи без истории удаления, поэтому случайное действие преподавателя было по сути необратимым.

Добавлен soft delete для `grades` и `grade_items`:
- `deleted_at`, `deleted_by_user_id`, `delete_reason`;
- `created_by_teacher_id` для привязки контрольной точки к владельцу;
- таблица `grade_events` для аудита действий: создание, обновление, удаление и восстановление.

Поведение теперь такое:
- преподаватель может удалить свою оценку или контрольную точку;
- если у контрольной точки уже есть активные оценки, удаление делается каскадно и это фиксируется в истории;
- восстановление контрольной точки и оценки вынесено в отдельные ручки;
- выборки в отчётах и агрегатах больше не подхватывают мягко удалённые записи.

Схема миграции и фильтрация активных записей выглядят так:

```sql
ALTER TABLE grade_items
    ADD COLUMN IF NOT EXISTS created_by_teacher_id INTEGER REFERENCES teachers(teacher_id) ON DELETE SET NULL,
    ADD COLUMN IF NOT EXISTS deleted_at TIMESTAMPTZ,
    ADD COLUMN IF NOT EXISTS deleted_by_user_id INTEGER REFERENCES users(id) ON DELETE SET NULL,
    ADD COLUMN IF NOT EXISTS delete_reason TEXT;

CREATE TABLE IF NOT EXISTS grade_events (
    event_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    grade_id INTEGER REFERENCES grades(grade_id) ON DELETE SET NULL,
    grade_item_id INTEGER NOT NULL REFERENCES grade_items(item_id) ON DELETE RESTRICT,
    student_id INTEGER REFERENCES students(student_id) ON DELETE SET NULL,
    actor_user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    event_type VARCHAR(40) NOT NULL
);
```

```go
rows, err := r.pool.Query(
```
