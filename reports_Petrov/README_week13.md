# Неделя 13 (26 мая - 2 июня 2026)

## Доработка API под Android и унификация регистрации

### 1. Цель недели

На этой неделе основной фокус был на том, чтобы привести backend к более единому и удобному контракту для мобильного клиента, при этом не сломав существующий веб-фронт.

Ключевые задачи:
- унифицировать регистрацию через invite-коды;
- добавить Android-совместимые ручки для создания занятий и отметки посещаемости;
- добавить загрузку аватаров;
- оставить старые сценарии работы преподавателя и студента совместимыми;
- подготовить архитектуру к дальнейшему переносу аватаров в S3.

### 2. Унификация регистрации

Была вынесена отдельная таблица приглашений для регистрации:
- `registration_invites`

Это позволило:
- хранить invite-коды отдельно от таблицы `students`;
- определять роль по записи в БД, а не по данным из запроса;
- поддержать не только студентов, но и преподавателей;
- переносить старые student invite-коды в новую схему без потерь.

Практический эффект:
- регистрация стала более предсказуемой;
- логика ролей перестала зависеть от ручных хэшей в запросе;
- старые данные не были потеряны при миграции.

### 3. Android-совместимые ручки

Добавлены и/или доработаны ручки под мобильный сценарий:
- `POST /lessons/create`
- `POST /api/student/mark-attendance`
- `POST /api/user/upload-avatar`

Эти ручки были сделаны как совместимый слой поверх текущей бизнес-логики, чтобы:
- Android-клиент получил понятный контракт;
- старый веб-поток продолжил работать;
- не пришлось переписывать все существующие сценарии.

Основная идея:
- веб-ручки остались как есть;
- Android получает отдельные endpoint-ы, но использует ту же доменную логику внутри backend-а.

### 4. Отметка посещаемости и антифрод

Для мобильной отметки посещаемости была добавлена поддержка:
- `lesson_id`
- `device_id`
- `lat`
- `lon`

Внутри backend теперь учитываются:
- привязка устройства к сессии;
- координаты занятия и точки отметки;
- подозрительные попытки отметить посещение;
- счетчик `total_cheat_attempts` у студента.

Что это дает:
- попытки фрода можно фиксировать отдельно;
- поведение студента становится наблюдаемым;
- мобильный сценарий становится ближе к реальной учебной модели, а не просто к "нажать кнопку".

### 5. Загрузка аватаров

Добавлен endpoint:
- `POST /api/user/upload-avatar`

Сейчас аватары сохраняются локально в директорию uploads, а затем отдаются по публичному URL.

Плюсы текущего решения:
- быстро реализуется;
- подходит для локальной разработки и небольшого продакшена;
- не требует отдельного сервиса на старте.

Минусы:
- при росте проекта и нескольких backend-инстансах локальная файловая система начинает мешать;
- бэкапы и масштабирование становятся сложнее.

### 6. Обновление ответа профиля

В профиле пользователя стали доступны дополнительные поля:
- `avatar`
- `group`
- `nfc_tag`
- `total_cheat_attempts`

Это полезно для Android-клиента, потому что UI может сразу получать больше данных без дополнительных запросов.

### 7. Техническая интеграция

Сделаны сопутствующие изменения в инфраструктуре:
- добавлен `UPLOAD_DIR` в конфиг;
- настроена раздача `/uploads`;
- обновлен `docker-compose.yml` для volume с аватарами;
- обновлен `nginx.conf` для проксирования `/uploads/` и `/lessons/`;
- обновлен Swagger, чтобы документация соответствовала текущим ручкам.

### 8. Проверка и валидация

После внедрения изменений были проверены основные сценарии:
- регистрация по invite-коду;
- создание занятия преподавателем;
- получение ссылки/QR на attendance;
- отметка посещаемости студентом;
- антифрод-сценарии по device_id и координатам;
- загрузка аватара и его отдача по публичному URL;
- совместимость старого веб-пути с новым API.

Техническая проверка:
- `go test ./...` — успешно;
- локальная интеграция с временной БД и backend-ом прошла успешно.

### 9. Итог недели

За неделю был сделан важный шаг в сторону единого API:
- регистрация стала более правильной с точки зрения БД;
- Android-клиент получил нужные ручки;
- old web flow не был сломан;
- аватары и профиль стали полноценной частью системы;
- backend стал ближе к удобной продакшен-архитектуре.

### 10. Планы на следующую неделю

Главный план на следующую неделю:
- подключить S3 для хранения аватаров и других медиа-файлов.

Что хочется сделать в рамках этого перехода:
- вынести хранение файлов в отдельный storage-слой;
- оставить совместимый API для frontend и Android;
- сделать локальное хранилище fallback-режимом для dev;

Ожидаемый результат:
- backend перестанет зависеть от локальной папки для медиа;
- система станет лучше масштабироваться;
