# Неделя 21

## Часть 1. Завершение работы с учебными семестрами

В прошлом отчёте была добавлена базовая сущность семестра и привязка к ней оценок и посещаемости. На этой неделе работа с семестрами была доведена до полноценного жизненного цикла. Теперь семестр может находиться в одном из четырёх состояний:

- `planned` — семестр создан заранее, но ещё не открыт;
- `open` — текущий семестр, в котором разрешено менять оценки и посещаемость;
- `closed` — завершённый семестр, доступный только для чтения;
- `archived` — архивный семестр для хранения истории.

В таблицу `semesters` добавлены статус, время последнего обновления и информация о том, кто создавал, открывал, закрывал и архивировал семестр:

```sql
ALTER TABLE semesters
    ADD COLUMN status VARCHAR(20),
    ADD COLUMN updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    ADD COLUMN created_by_user_id INTEGER REFERENCES users(id),
    ADD COLUMN opened_at TIMESTAMPTZ,
    ADD COLUMN opened_by_user_id INTEGER REFERENCES users(id),
    ADD COLUMN closed_at TIMESTAMPTZ,
    ADD COLUMN closed_by_user_id INTEGER REFERENCES users(id),
    ADD COLUMN archived_at TIMESTAMPTZ,
    ADD COLUMN archived_by_user_id INTEGER REFERENCES users(id);
```

На уровне базы данных добавлены ограничения: одновременно открытым может быть только один семестр, учебный год должен иметь формат `YYYY/YYYY`, а даты разных семестров не должны пересекаться.

## Часть 2. Безопасное переключение и закрытие семестра

Переключение активного семестра теперь выполняется транзакционно. Перед открытием нового периода предыдущий открытый семестр закрывается. Если в текущем семестре ещё работает сессия посещаемости, переключение или закрытие блокируется, чтобы не потерять отметки студентов во время занятия.

Добавлены отдельные административные маршруты:

- `POST /api/admin/semesters` — создать запланированный или сразу открытый семестр;
- `PATCH /api/admin/semesters/:semester_id/activate` — открыть запланированный семестр;
- `PATCH /api/admin/semesters/:semester_id/close` — закрыть текущий семестр;
- `PATCH /api/admin/semesters/:semester_id/archive` — перенести закрытый семестр в архив.

Для создания семестра проверяются формат учебного года, номер семестра, длина названия, диапазон дат и соответствие дат учебному году. Нельзя открыть семестр, который ещё не начался или уже закончился.

```go
func semesterWriteError(semester db.Semester, now time.Time) error {
    if semester.Status != db.SemesterStatusOpen || !semester.IsCurrent {
        return errors.New("semester is not open for changes")
    }
    if now.Before(semester.StartsAt) {
        return errors.New("semester has not started")
    }
    if !now.Before(semester.EndsAt) {
        return errors.New("semester has ended")
    }
    return nil
}
```

## Часть 3. Защита учебных данных закрытого семестра

Расписание теперь тоже связано с семестром через `semester_id`. При импорте расписания без указанного периода база автоматически использует открытый семестр. Если открытого семестра нет, импорт останавливается с ошибкой.

Для оценок, контрольных точек и посещаемости добавлены триггеры базы данных. Они разрешают запись только в открытый текущий семестр, даты которого уже начались и ещё не закончились. Поэтому изменить данные закрытого периода нельзя даже в случае ошибки в сервисном коде или прямого SQL-запроса.

```sql
PERFORM 1
FROM semesters sem
WHERE sem.semester_id = target_semester_id
  AND sem.status = 'open'
  AND sem.is_current = TRUE
  AND now() >= sem.starts_at
  AND now() < sem.ends_at;

IF NOT FOUND THEN
    RAISE EXCEPTION 'semester is not open for changes';
END IF;
```

## Часть 4. Первый CRUD для административной панели

Начата backend-часть административной панели. Первым модулем сделано управление пользователями. Добавлены пять маршрутов:

- `GET /api/admin/users` — список пользователей;
- `GET /api/admin/users/:user_id` — получение одного пользователя;
- `POST /api/admin/users` — создание пользователя;
- `PATCH /api/admin/users/:user_id` — изменение пользователя;
- `DELETE /api/admin/users/:user_id` — архивирование пользователя.


При создании учитывается роль пользователя:

- для студента создаётся профиль студента и при необходимости указывается группа;
- для преподавателя создаётся профиль преподавателя с кафедрой и должностью;
- для заведующего указывается кафедра;
- для декана указывается факультет;
- для администратора отдельный учебный профиль не требуется.

Пользователь и его профиль создаются одной транзакцией. Если профиль создать не удалось, учётная запись тоже не сохраняется.

## Часть 5. Статусы пользователей и защита администратора

В таблицу `users` добавлены поля `status` и `updated_at`. Используются три состояния:

- `active` — обычная активная учётная запись;
- `blocked` — временно заблокированный пользователь;
- `archived` — мягко удалённый пользователь.

Физическое удаление не используется, потому что пользователь может быть связан с оценками, посещаемостью и другими историческими данными. Метод `DELETE` переводит запись в состояние `archived`.

При каждой проверке токена backend дополнительно загружает пользователя из базы. Если пользователь заблокирован или архивирован, старый JWT сразу перестаёт давать доступ:

```go
if dbUser.Status != "active" {
    return User{}, errors.New("account is not active")
}
```

Также добавлены ограничения для администратора:

- обычные роли не имеют доступа к `/api/admin/users`;
- администратор не может архивировать собственную учётную запись;
- администратор не может изменить собственную роль или статус;
- нельзя заблокировать или лишить роли последнего активного администратора;
- пароль сохраняется только в виде bcrypt-хеша.
